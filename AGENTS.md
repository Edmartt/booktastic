# AGENTS.md

Booktastic is a Go microservices project (`books-service`, `books-auth`) behind Traefik, plus a local `shared` module. The repository has no root `go.mod`/`go.work`: each directory is its own module, so run Go commands from the module directory, not the repo root.

## Layout

- `books-service/` — books API, hexagonal architecture: `internal/core/{domain,ports}` for business code, `internal/adapters/{http,database,repository}` for infrastructure. Entrypoint: `main.go`.
- `books-auth/` — auth API exposing signup/login and the Traefik forward-auth `verify` endpoint. Auth0 is isolated behind interfaces in `internal/core/ports` and selected in `internal/adapters/factory.go`.
- `shared/` — Gin error writer. Both services import it through `replace github.com/edmartt/booktastic-shared => ../shared`, so shared changes are picked up without publishing.
- The books-service module path is `github.com/edmartt/bookstatic-book-service` (note `bookstatic`) — use it verbatim in imports.

## Commands

```bash
cd books-service && go build ./... && go test ./...
cd books-auth    && go build ./... && go test ./...
cd shared        && go build ./...
```

- Handler tests for `books-service` live in `internal/adapters/http/`: `handlers_test.go` groups every handler-specific router, request helper, fixture and test (ReadBook, CreateBook); `test_helpers_test.go` holds the shared infrastructure — `TestMain` (sets `gin.TestMode`), the `fakeBookRepository` (which panics when an operation function is not configured) and generic response helpers. They use `testify`. CI (`.github/workflows/golangci-lint.yml`) only runs golangci-lint v2.4.0 for `books-service` and `books-auth`, with no repo-local lint config.
- Single test / focused run: `go test ./internal/... -run TestName`.
- On Windows, the books-service default build fails in `mattn/go-sqlite3` without gcc/cgo. Use `CGO_ENABLED=0 go build ./...` to compile (the SQLite driver then fails only if used at runtime).
- Full stack: copy `.env.example` to `.env`, fill Auth0/Postgres values, then `docker compose up --build`.
- Dockerfiles use paths relative to the repo root and copy `shared/`; build them with the repo root as context, e.g. `docker build -f books-service/dockerfile .` (that is what compose does).

## Runtime gotchas

- Each service loads `.env` only if it exists in the current working directory. `books-service` Postgres settings are `PG_USER`, `PG_DB`, `PG_PASSWORD`, `PG_HOST` and `PG_PORT` (the unprefixed `HOST`/`PORT` names are no longer read), plus `HTTP_PORT` for the server; all are required.
- `books-service/main.go` always starts the Postgres adapter. The SQLite adapter and `dbconfig.yml` sqlite3 environment exist but are not wired into `main.go`.
- Migrations run via sql-migrate in the compose `migrate` service (`sql-migrate up -config=dbconfig.yml -env=production`). Add new timestamped files under `migrations/postgres/`; update `migrations/sqlite3/` too if maintaining the dev schema (it currently lacks `user_id`).
- Traefik's forwardAuth calls `books-auth` `/api/v1/auth/verify`, which returns the user id as `X-User-Id`; books handlers read that header. Running `books-service` directly bypasses auth, so set `X-User-Id` manually or book creation returns 500.
- Actual book route is `PATCH /api/v1/books/:id` even though the README and a swagger annotation say `PUT`. Swagger UI is served at `/api/v1/swagger/index.html` (README's URL omits the prefix).
- Swagger files in `*/docs/` are generated by swaggo/swag. Edit annotations in `internal/adapters/http/handlers.go` and `main.go`, then run `swag init` inside the service directory; do not hand-edit `docs/`.

## Conventions

- Keep `internal/core` free of Gin, SQL, and Auth0 types; add new infrastructure behind a port interface and wire it in `main.go` or the factory.
- Handlers report errors through `shared/errors/http/adapters/ginhttp.GinErrors.WriteError`, producing `{"message": "..."}`.
- Do not import Auth0 directly into handlers; extend `adapters.NewAuthProvider` instead.
- Books are user-scoped: `Read` filters by `uuid` + `user_id`, and `Create` stores `user_id`. `Update` currently matches on `uuid` only and relies on the handler's prior scoped `Read`; preserve that ordering unless you add user scoping to the query.
